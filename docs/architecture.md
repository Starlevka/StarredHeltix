# Архитектура и принципы оптимизации

Здесь — внутренний архитектурный гайд для разработчиков мода StarredHeltix.
Если ты пользователь и ищешь команды или список фич — см. `README.md`.

---

## Философия мода

- Клиентский мод для удобной игры на сервере Heltix Skyblock (`heltix.net`, `starlev.heltix.net`).
- Качество жизни (QOL): автоматизация рутины, визуальные улучшения, решатели головоломок, HUD-элементы.
- Приоритет — **стабильность и производительность**: мод не должен ронять FPS и не должен крашить клиент.

---

## Архитектурные слои

```
Событие Minecraft
       ↓
Миксин (Java)              ← доступ к приватным полям/методам игры
       ↓
Детектор (Kotlin, object)   ← парсит событие, публикует доменный факт
       ↓
Фича (Kotlin, object)       ← реагирует на факт, обновляет состояние
       ↓
HUD / Render / Chat         ← отображает состояние игроку
```

- **Миксины** — только ради доступа к приватным методам/полям. Бизнес-логики в них нет.
- **Детекторы** (`utils/detectors/*`) — точка перехода от «сырых событий Minecraft» к «доменным фактам Skyblock».
- **Фичи** (`features/<domain>/*`) — реагируют на факты детекторов и держат состояние.
- **HUD/Render** — читают состояние фич, рисуют.

## Реестр фич и авто-инициализация

Список фич живёт в [`src/main/kotlin/set/starlev/features/FeatureBootstrap.kt`](../src/main/kotlin/set/starlev/features/FeatureBootstrap.kt) — **единственное место**, куда добавляются новые фичи при старте. Подробнее — в [`cookbook.md`](cookbook.md).

Порядок регистрации важен: детекторы раньше фич, которые на них подписываются.

## Принципы оптимизации (из опыта SB модов)

Эти принципы выработаны на основе практик крупных Skyblock модов (SkyHanni, Odin, Firmament). Цель — поддерживать высокий FPS и стабильность игры.

### 1. Событийная модель (event-driven) вместо циклов (polling)

- **Избегаем** сканирования мира/сущностей в `onTick` или `onRender`.
- **Подписываемся** на события пакетов (`ClientReceiveMessageEvents`, `ClientboundAddEntityPacket`) для обнаружения объектов (например, Эндер-нод или Грибов).

### 2. Умное кэширование и валидация

- Найденные позиции сохраняем в кэш с меткой времени.
- В тиках проверяем **только уже найденные** объекты («стоит ли ещё блок по этому адресу?»), а не ищем новые с нуля.
- Сбрасываем кэш при смене мира или локации (`onWorldChange`).

### 3. Пакетная отрисовка (batch rendering)

- Не вызываем тяжёлые методы отрисовки (`graphics.fill`, `BufferBuilder.end`) для каждого отдельного объекта.
- Собираем данные для рендера в списки в течение кадра и отрисовываем всё за один проход в конце (`RenderEvent.Last`).

### 4. Фильтрация на уровне пакетов

- Если объект не должен отображаться (скрытие частиц, падающих блоков, определённых сущностей), отменяем пакет его спавна. Это экономит ресурсы на создание объекта в памяти Minecraft.

### 5. Эффективный доступ к конфигурации

- Избегаем сложных вычислений или парсинга строк конфига внутри рендера.
- Кэшируем значения настроек в простые переменные (`Boolean`, `Int`) при изменении конфига.

### 6. Защита hot-path от лишних вызовов

- В тиках и render-callback'ах **не вызываем функции**, которые заведомо вернут `false` (выключенный дев-лог, выключенный детектор и т.п.).
- Шаблон: один раз в начале тика проверяем общий флаг `if (Feature.isAnyEnabled()) { ... }`, а внутри каждой функции — точечный guard. Так в горячем пути остаётся одна проверка вместо четырёх.

## Зависимости между подсистемами

| Подсистема | Зависит от | Заметки |
|------------|-----------|---------|
| Миксины | Minecraft API | Только мост к приватным методам |
| Детекторы | Миксины (через события) | Парсят сырые события |
| Фичи | Детекторы, ConfigManager | Реагируют на факты |
| HUD | Фичи (через состояние) | Рендер |
| ConfigManager | — | Загружается первым |
| EntityRegistry | — | Регистрирует сущности до рендереров |

## Замечания по потокобезопасности

- Миксины выполняются в основном игровом потоке.
- Сетевые события (`ClientReceiveMessageEvents`) — тоже в основном потоке Minecraft.
- `Minecraft.getInstance().execute { ... }` — для отложенного выполнения в основном потоке из других источников.
- Состояние детекторов и фич должно быть либо immutable, либо синхронизировано через `@Volatile`.
